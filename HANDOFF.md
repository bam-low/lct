# Хэндовер для второго разработчика

Этот файл — не замена README.md (там структура каталогов и запуск), а более
практический документ: что уже сделано, что осталось по ТЗ, как устроен код
изнутри и на что обратить внимание, если продолжаешь эту часть проекта
(визуализация + экономика). Роли/аккаунты/бэкенд/БД — не эта часть, см. ниже.

Дата: 2026-09-28/29. ТЗ: `тз/1. ФЦ БАС.pdf` (в git не закоммичен — папка `тз/`
содержит 84 МБ PDF-каталог, добавлена в исключения; если нужен git — см. низ файла).

## 1. Что уже готово

- **Склад** — полностью рабочий сценарий: конструктор произвольной формы
  (рисуемый пиксель-арт), 3 типа роботов (пылесосы/роборуки/погрузчики) с
  реальными и процедурными 3D-моделями, экономика (CAPEX/OPEX/TCO/ROI/
  payback), сравнение 3 сценариев, чувствительность к параметрам, симуляция,
  подтверждающая расчёт («Нужно / Расчёт парка / В симуляции»).
- **Аэропорт** — бета: один процесс (транспортировка), 3D-сцена с посадкой
  самолётов, багажными тягачами, той же экономической моделью. Не так
  функционально насыщен, как склад, но рабочий и без известных багов.
- **Медучреждение** — не начато, в UI помечено «скоро». По ТЗ п.2 обязателен
  только ОДИН тип объекта из трёх (или свой) — склад с запасом перекрывает
  этот минимум, поэтому медучреждение не блокер сдачи, а просто следующий
  шаг, если останется время.

## 3. Как устроен код

### 3.1. Слои (снизу вверх, каждый не знает о более высоком)

```
domain/        — чистые функции и данные, без React/Three.js
  economics.js, scenarioEngine.js  — формулы CAPEX/OPEX/TCO/ROI/payback (ТЗ 3.5.2), не знают про тип объекта
  catalog.js                        — демо-каталог решений (все позиции — vendor/technical/economics/applicability)
  ranking.js                        — объяснимое ранжирование каталога (индекс эффективности)
  applicability.js                  — проверка ограничений решения против параметров объекта
  objectTypes.js                    — схема параметров (paramSchema) на тип объекта — форма ввода строится из неё
  warehouseAdapter.js, airportAdapter.js — переводят параметры объекта + каталог в input для economics.js
  paramsFile.js                     — CSV-шаблон параметров (экспорт/импорт), downloadTextFile

state/          — React-хуки состояния
  useEconomicsState.js, useAirportEconomicsState.js — вся бизнес-логика экрана: выбранные решения,
                                                        сценарии, layout, персист в localStorage (projectStore.js)

simulation/     — 3D (Three.js), ЧИТАЕТ state, никогда не пишет экономику обратно
  layout.js, shape/                — геометрия склада; shape/ — рисуемая форма (см. 3.2)
  useSimulation.js                 — главный хук сцены склада: собирает флоты роботов по параметрам
  vacuums/, arms/, loaders/        — три флота (у каждого свой файл createXFleet + свой автомат состояний)
  robots/                          — 3D-модели: обёртки над public/models/*.glb ИЛИ процедурная geometry
  airport/                         — параллельная сцена аэропорта (useAirportSimulation3D.js — тот же паттерн)

apps/           — WarehouseApp.jsx / AirportApp.jsx: экран setup → results, склеивают state + simulation + UI
components/     — переиспользуемые куски UI (economics/, ui/, warehouse/ShapeEditor.jsx)
App.jsx         — роутер по objectTypeId (warehouse/airport/…)
```

### 3.2. Конструктор формы склада (`simulation/shape/`)

Форма — `{ gridSize, cellSize, cells: Uint8Array }`, ячейки — `CELL.{EMPTY,
FLOOR, GATE, RACK, GATE_IN, GATE_OUT}` (`shapeTypes.js`). Стандартный
прямоугольник — просто заранее заполненная сетка (`buildDefaultShape()`),
не отдельная ветка кода. `shapeGeometry.js` — вся геометрия, выводимая из
сетки: `boundingBoxOf`, `computeGateClusters` (кластеризует клетки ворот,
определяет `kind: 'in'|'out'|'generic'`), `computeWallSegments`,
`computeRackObstacles` (прямоугольники-препятствия для объезда, новое
сегодня — см. 3.4). `isDefaultShape(shape)` — структурное сравнение с
пресетом, используется везде, где логика должна отличаться на своей форме
(погрузчики, стеллажи).

**Важно**: `GATE_OUT` = «зона загрузки» (склад → фура, товар увозят),
`GATE_IN` = «зона выгрузки» (фура → склад, товар привозят). Легко перепутать
на слух — см. `ShapeEditor.jsx` TOOLS, там подписано явно с стрелками.

### 3.3. Три флота роботов склада

Общий паттерн: `createXFleet({ group, zone/gates, count, ...,
robotFactory })` → возвращает `{ step(dt), getStats(), dispose(), meters,
obstacles? }`. `useSimulation.js` вызывает `step()` каждый кадр, собирает
`getStats()` в общий `simStats.js`. `robotFactory` — какую 3D-модель
построить на каждое место; по умолчанию процедурная, альтернативы — реальные
GLB-модели пользователя (см. `ARM_FACTORIES`/`VACUUM_FACTORIES`/
`LOADER_FACTORIES` в `useSimulation.js`, ключ — `identification.type` из
каталога).

Ветвления по типу решения, не по типу объекта — прямая параллель:
- `armType === "stacker"` → `arms/stackerFleet.js` вместо `arms/armFleet.js`
  (у модели своя мини-лента, парные конвейеры не нужны).
- `loaderType === "storagecube"` → `loaders/storageCubeFleet.js` вместо
  `loaders/loaderSystem.js`/`customLoaderFleet.js` (стационарная сетка башен
  + один шаттл сверху, не ездит по складу).
- `isDefaultShape(shape)` решает `loaderSystem.js` (полноценные проезды) или
  `customLoaderFleet.js` (упрощённый маршрут ворота↔стеллаж) для обычных
  погрузчиков/транспортировщиков.

### 3.4. Реальные GLB-модели пользователя — как подключать новую

Шаблон (см. `robots/weldArmRobot.js`, `robots/stackerRobot.js`,
`robots/storageCubeRobot.js`):

1. Файл в `public/models/<name>.glb`.
2. `export const xModel = createGlbModel("<name>.glb", normalizeModel);`
   (`glbModel.js` — общая загрузка, кэш, `normalizeModel` центрует по XZ и
   ставит низ модели на y=0).
3. Добавить в `MODELS` в `robots/models.js` (иначе не прогреется заранее).
4. **Перед тем как встраивать модель в существующий флот — узнай, что она
   реально изображает.** Инструмент: распаковать GLB (это ZIP-подобный
   бинарный контейнер) и прочитать JSON-чанк — там имена узлов на русском,
   которые задавал автор модели, и они обычно прямо говорят, что где
   (см. пример ниже). НЕ надо гадать по картинке/скриншоту.

   ```js
   const buf = fs.readFileSync(path);
   let offset = 12, json = null;
   while (offset < buf.length) {
     const len = buf.readUInt32LE(offset);
     const type = buf.toString('ascii', offset + 4, offset + 8);
     if (type === 'JSON') json = JSON.parse(buf.toString('utf8', offset + 8, offset + 8 + len));
     offset += 8 + len;
   }
   console.log(json.nodes.map(n => n.name));
   ```

5. Если модель — самодостаточный узел (своя механика уже внутри файла, как
   у `stacker.glb`/`storage_cube.glb`) — не пытайся встроить её как «кисть»
   на процедурный каркас (это и была сегодняшняя ошибка с «Ручка WA-1» —
   реальную модель насаживали на конец нарисованной вручную роборуки, и
   получалось «два робота», один носит другого). Вместо этого — либо
   отдельный флот (`stackerFleet.js`), либо, если механика простая (одна
   ось вращения) — обёртка `THREE.Group()`-pivot с фиксированной
   компенсацией разворота внутри (`floorWasherRobot.js` — пример, когда
   fleet каждый кадр перезаписывает `model.rotation.y` напрямую, поэтому
   разворот-компенсация должна быть на ДОЧЕРНЕМ объекте, а не на самом
   возвращаемом узле, иначе слетит на первом же кадре).
6. Если у узла есть «странный» выброс координат (одна деталь торчит на
   много единиц в сторону/вниз от остального) — это может быть огрех самого
   файла, не архитектурная особенность. Меряй `Box3.setFromObject` с
   ПОДОЗРИТЕЛЬНЫМ узлом скрытым (`node.visible = false`), не доверяй
   границам модели целиком не глядя — см. `storageCubeFleet.js`, комментарий
   у `BOX_RISE_LOCAL` (узел «БОКС» в `storage_cube.glb` стоит на ~12 единиц
   ниже всего остального — settled на фиксированный визуально подобранный
   ход вместо честного расчёта по границам).

### 3.5. Экономика (`domain/`, `state/`)

`useEconomicsState.js` — источник истины для экрана склада: параметры
(`params`), выбранные решения (`selectedSolutions`), три сценария
(`scenarios.baseline/purchase/raas`), состав парка (`counts`,
`recommendedCounts`, `totalCounts` — на всё здание с учётом этажей). Формулы
считаются в `domain/economics.js` + `scenarioEngine.js`, не знают о складе
конкретно — адаптер (`warehouseAdapter.js`) переводит `params` +
`selectedSolutions` в вход для этих формул (пиковый спрос по процессам,
энергопрофили, `computeLayout(shape, ...)` для геометрии).

Числа для симуляции (`armCount`, `armProd` и т.п.) идут из ЭТОГО ЖЕ состояния
в `WarehouseScene`/`useSimulation.js` — экономика и визуализация никогда не
считают независимо, поэтому панель «Подтверждение расчёта симуляцией»
осмысленна (кроме одного нового исключения, см. ниже).

## 4. Известные ограничения и технический долг (честно)

- **СтойкаБокс и «расчёт парка» разошлись.** Раньше `count` независимых
  башен = `count`× пропускной способности (каждая со своим лифтом). Сегодня
  по прямой просьбе пользователя переделано в плотную сетку башен + ОДИН
  шаттл сверху (реалистичнее для настоящего AS/RS, но throughput теперь
  физически не масштабируется с `count` так же линейно). Экономика
  (`requiredRobotCount`) по-прежнему считает `count` как N независимых
  единиц — числа «Нужно/Расчёт парка» и «В симуляции» для этого решения
  могут расходиться сильнее, чем для остальных. Не баг симуляции — баг
  несоответствия между экономической моделью (линейное масштабирование) и
  новой архитектурой (один шаттл). Если это важно для итоговой сдачи —
  обсудить с командой, возможный фикс: либо считать для storagecube throughput
  иначе (не через стандартный `requiredRobotCount`), либо явно
  задокументировать в UI, что storagecube — capacity-решение, а не
  throughput-решение.
- **Объезд препятствий у погрузчиков на своей форме — не полноценный
  pathfinding.** `customLoaderFleet.js` (`computeDetourWaypoint`) объезжает
  ОДНО препятствие на прямом участке пути (ставит одну промежуточную точку
  сбоку). Если между воротами и стеллажом несколько чужих стеллажей подряд —
  объезд первого может завести прямо во второй. Для типичных раскладок
  (стеллаж закреплён за ближайшими воротами) это редкий случай, но не
  исключён на специально запутанной форме. Полноценная сетка/A* — не
  сделана, сознательно (см. план конструктора формы склада ещё с первой
  версии).
- **LowCart (транспортировщик) и АкваБот (мойщик полов)** — сегодня
  увеличен масштаб LowCart (`TRANSPORTER_MODEL_SCALE` в `constants.js`) и
  добавлена компенсация разворота АкваБота (`FORWARD_CORRECTION_Y` в
  `floorWasherRobot.js`, -90°) — оба правились «на глаз» по описанию
  проблемы автором модели, БЕЗ финальной визуальной проверки в браузере (не
  хватило времени/инструмент не давал приблизить картинку по пикселям).
  Код корректен по логике, но если масштаб/разворот всё ещё не тот —
  правка в одну строку в `constants.js`/`floorWasherRobot.js`.
- **`тз/` не в git** — 84 МБ PDF, исключена из коммитов. Если нужна на
  другой машине — передать отдельно или добавить Git LFS.

## 5. Проверка перед сдачей

```bash
npm run lint     # oxlint — должно быть чисто
npm run build    # прод-сборка — должно быть чисто, только предупреждение про размер чанка (ок)
npm run dev      # ручная проверка в браузере
```

Ручной прогон, на который стоит потратить 10 минут: склад → своя форма
(нарисовать несколько ворот разных типов + стеллажи) → каждый тип роботов по
отдельности и все сразу → экран результатов → проиграть на 128× и убедиться,
что нет ошибок в консоли и роботы визуально не проезжают сквозь стеллажи.
Аэропорт — аналогично, гейты/транспортировщики в разном количестве.
